# GPU vs CPU pe operațiile reale din proiect, 2026-11-01

## Concluzie

**GPU nu se activează în producție.** Mașina are NVIDIA GeForce RTX 5060 Ti 16 GB
(CUDA 13.5), testat cu CuPy 14.2 (cupy-cuda13x) într-un venv separat — venv-ul
de producție rămâne CPU-only, nemodificat. Pe căile fierbinți din pipeline GPU
este mai lent decât CPU; câștigă doar la enumerarea exhaustivă mare, pe care
producția nu o folosește (avem numărătoare combinatorială exactă, mai rapidă).

## Numere (RTX 5060 Ti vs CPU numpy 2.5, același cod rulat cu numpy/cupy)

| workload | CPU | GPU | verdict |
|---|---:|---:|---|
| A operații mici per apel scorer (2600×49, 1000 iterații) | 47 µs | 219 µs rezident / 281 µs cu transfer | **CPU ×4–6** |
| B MI pe fereastră (2600 zile × (500×49)ᵀ@(500×49)) | 0,082 s | 0,153 s | **CPU ×1,9** |
| C `_hit_counts` v=16 (2^16, 152 bilete) | 1,0 ms | 32 ms (steady-state) | **CPU ×30** |
| C `_hit_counts` v=20 (2^20) | 18,7 ms | 2,8 ms | GPU ×6,7 (singurul hit-count mare) |
| D enumerare exhaustivă C(49,6)=13.983.816 extrageri × 152 bilete | 20,0 s | 6,8 s | GPU ×2,9 |
| E matmul dens 4000³ float64 | 364 ms | 404 ms | egal (fp64 limitat pe placa consumer) |

Sanity: histograma de hituri din D e identică CPU/GPU și suma = C(49,6);
hist[6] = 152 = biletele însele. Numărătoarea combinatorială exactă din
`covering.probability` face același lucru în 1 ms (v=16), deci enumerarea
(6,8–20 s) rămâne doar pentru audit offline.

## De ce GPU pierde aici

Pipeline-ul e dominat de **operații mici, multe, cu bucle Python** (scoreri per
zi, ferestre glisante): fiecare kernel GPU are overhead de launch ~5–20 µs și
transfer PCIe, deci la (2600×49) CPU câștigă. Placa consumer are și fp64
limitat, deci nici matmul-urile dense mari nu câștigă (E). GPU ar ajuta doar
la batch-uri mari de același kernel (D, C la v=20).

## Biblioteci GPU luate în considerare (2026)

- **CuPy** (drop-in numpy pe CUDA) — testat aici; bun pentru batch-uri mari,
  prost pentru operații mici. Singura opțiune rezonabilă fără a rescrie codul.
- **PyTorch / JAX** — pentru antrenare de rețele; proiectul interzice explicit
  stack-ul neural/GPU (AGENTS.md §10), iar metodele sunt deliberate CPU ieftine.
- **RAPIDS (cuDF/cuML)** — DataFrame/ML pe GPU; nu avem DataFrame-uri mari.
- **XGBoost/LightGBM GPU** — doar pentru modele arboresc mari; nu e cazul.
- **numba.cuda** — aceleași concluzii ca CuPy, cu cost de compilare.

Decizie: **stack-ul rămâne CPU-only**; GPU se poate activa ulterior doar pentru
audit offline de tip D (enumerare exhaustivă), caz în care se rulează scriptul
din venv-ul separat, nu în producție.
