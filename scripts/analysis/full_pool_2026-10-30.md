# Pool pana la 49 / 40 / 45 — 30.10.2026

Cerinta utilizatorului: pool extins configurabil pana la maximul fiecarui
joc romanesc, cu valorile implicite actuale pastrate. Alegerea explicita a
maximului inlocuieste vechea limita data de catalogul schemelor LR.

## Setari si motor

`Lottery.max_pool` este 49 / 40 / 45 pentru Romania; `default_pool` ramane
16 / 19 / 15. Celelalte tari raman la maxim 16. Incarcarea setarilor,
configuratia taskurilor si workerul folosesc acelasi registru. Modificarea
nu rescrie setarile utilizatorului si nu schimba optiunile implicite.

Peste 19 numere, `covering.large_pool` construieste un cover determinist pe
pozitii, apoi il transpune pe clasamentul numerelor. Fiecare pas adauga un
bilet care acopera cel putin o grupa inca neacoperita. Fara plafon termina
coverul; cu plafon poate avea acoperire partiala. Nu este o cautare a
coverului minim si nu promite imbunatatirea ratei de castig la acelasi cost.

Constructia nu aloca toate C(v,pick) biletele sau un vector de 2^v elemente.
Uniunea grupelor de garantie este numarata exact. Pentru „g daca c”, grupele
conditiei sunt parcurse in loturi NumPy de 32768 de randuri, cu index
combinadic. Nu se estimeaza acoperirea prin esantionare.

Protectiile noii rute sunt explicite: cel mult 100000 de variante cerute;
un sistem complet nelimitat de cel mult 100000 de variante; cover nelimitat
de cel mult 250000 de grupe tinta; calcul conditional de cel mult 20 milioane
de grupe. Cererile care depasesc aceste limite dau eroare cu explicatie si
solutia de reducere a plafonului, garantiei sau conditiei. Nu se taie pool-ul.
Campul existent din UI permite plafonul 1..10000 sau 0 pentru nelimitat.

Limita optionala de consecutive pastreaza regula existenta: se relaxeaza
pentru a incapea numerele cerute. Auditul arata limita ceruta si cea efectiva.
Pe intreg universul, toti candidatii sunt selectati indiferent de scorer.
Numerele din pool care nu incap pe bilete la un plafon mic raman enumerate.

## Istoric si prezentare

Pentru pool efectiv peste vechile limite ale UI (16 / 19 / 16), walk-forward
cere plafon pozitiv. Numarul
extragelor valide obtinut din `simulation_indices` inmultit cu plafonul
trebuie sa fie cel mult 1500000. Cererile mai mari sunt sarite explicit,
fara cache incarcat/scris, fara rezultate zero fabricate si fara relansari
repetate de temporizatorul interfetei. Utilizatorul poate reduce plafonul
sau adancimea istoricului. Pool-urile vechi isi pastreaza comportamentul.

Decizia de scoring poate proveni de la cel mai apropiat pool deja evaluat,
cu nota explicita; ratele lui nu sunt prezentate ca validare a noului pool.
Baseline-ul hipergeometric al pool-ului se poate calcula pentru orice marime.
Calculul exact al sansei comune pe variante ramane pana la pool 20; interfata
explica de ce pentru pool mai mare afiseaza numai sansele pool-ului.
Acoperirea wheel-ului ramane calculata exact, fiind un indicator diferit.

„Bilet complet” pastreaza limita lui de 16, anuntata deja in rezultat.
Catalogul LR ramane nemodificat; noile variante nu primesc un cod LR fictiv.
Workerul foloseste `lp1` peste vechile maxime 16 / 19 / 16, fiindca o cerere
bruta de 17 la 6/49 putea avea un rezultat vechi plafonat la 16. Semnatura
wheel-ului WF foloseste `lp1` numai peste 19, unde se schimba algoritmul.
Cheile configuratiilor valide anterior sunt identice.

## Verificare

Lucrul se face intr-un snapshot local al commitului a19b01c, separat de
aplicatia activa, pe CPython 3.14.10 x64. Testele noi verifica acoperirea
independent, pool-urile maxime, bugetele, cererile prea mari, integritatea
Joker si relaxarea consecutivelor in pipeline, persistenta setarilor,
workerul, cache-ul, istoricul si prezentarea rezultatelor.

Benchmark reproductibil, independent de istoric:

```powershell
python -m scripts.analysis.benchmark_large_pool_2026_10_30
```

Pe statia curenta, constructia rece a coverului complet de 4 a produs
29307 / 26351 / 42937 de variante pentru pool 49 / 40 / 45, cu acoperire
exacta 100%, in aproximativ 2 / 2 / 3,3 secunde. Cu plafon 10000, acoperirile
sunt 58,21% / 51,14% / 32,93%. Acestea sunt acoperiri ale grupelor din pool,
nu rate de castig la o extragere. Timpii sunt locali, nu garantii de durata.

Browserul a verificat implicitele 16 / 19 / 15, limitele atributelor HTML
49 / 40 / 45, acceptarea maximelor si persistenta lor dupa reincarcare, in
setari separate de productie. Serverul temporar a fost oprit dupa verificare.

Un worker real, pornit separat pe o coada SQLite izolata, a procesat toate
istoricele celor trei jocuri (2597 / 1748 / 2200 de randuri), cu pool-urile
49 / 40 / 45 si plafon 112. Rezultatul COMPLETED a fost recitit si decodat
din SQLite dupa oprirea procesului. Toate numerele sunt in pool si pe bilete;
variantele sunt distincte, Joker corect, iar acoperirile coincid cu numararea
independenta. Cele 19 fisiere protejate au aceleasi amprente inainte si dupa.

Auditul general: 13 istorice, 848 comparatii de scoruri, 154 de designuri,
26 de pipeline-uri, 13 profile de cover complet, worker pe 13 jocuri,
UI HTTP 200 si fisiere protejate nemodificate. Revizia separata a verificat
330 de geometrii de pool mare si cazuri conditionale cu formula inchisa.
Problema gasita in review (bench neetichetat pentru noile 17..19 la 6/49 si
Joker) este reparata si acoperita de teste. Protectia WF se aplica si acestor
marimi noi, pastrand vechile configuratii valide.

Validare cumulata pe Windows / CPython 3.14.10: 3896 de teste distincte
trecute, 20 sarite. Rularea integrala initiala (17 min 29 s) a avut 3882
trecute, 20 sarite si o asertiune veche care cerea plafonarea lui 19 la 16
in tabelul de intervale. Asertiunea a fost actualizata pentru noua cerinta.
Cele 58 de teste reluate dupa ajustarile finale au trecut, inclusiv cazul
respectiv si cele 13 cazuri noi adaugate in timpul reviziei. Colectia finala
are 3916 de cazuri; numarul cumulat nu numara reluarile de doua ori.

Sintaxa celor 24 de fisiere Python si `git diff --check` trec. Fisierele de
productie se copiaza numai dupa compararea cu baza testata; istoricele,
setarile si rezultatele locale de benchmark nu se comit. Aplicatia activa
nu este repornita de aceasta lucrare; schimbarile intra la repornirea normala.
